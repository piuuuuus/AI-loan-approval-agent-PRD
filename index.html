一、背景

本 PRD 为 AI 产品立项文档。立项主体假设为某持牌消费金融公司，业务为个人消费贷（现金分期/信用贷），本产品通过大语言模型 Agent 辅助人工审批，在合规前提下提升审批效率与质量。

1.1 业务背景

业务现状与痛点

公司个人消费贷业务当前采用"全人工审批"模式：

  • 审批时效长：单笔审批时效 T+1 ~ T+3 天，客户体验差，流失率高（申请到放款的转化率仅约 40%，超半数流失发生在"等待审批"环节）。
  • 人工成本高：日进件量约 2 万笔，审批团队约 80 人，人均日处理约 250 笔，单笔人工成本约 15 元；高峰期（大促、发薪日）进件积压严重，需临时扩编或加班。
  • 审批尺度不一致：同一 case 由不同审批员处理，结论一致率仅约 85%。审批员需要手动翻阅征信报告、银行流水、收入证明等 5-8 类材料，单笔材料阅读耗时约 20 分钟，其中约 60% 是机械性的信息核对与摘录工作，风险判断与决策只占少数时间。
  • 监管对可解释性要求高：拒件必须向客户提供可解释的理由（《个人贷款管理办法》《征信业务管理办法》相关要求），人工撰写拒件解释耗时且口径不一，易引发投诉。

机会点

大语言模型在长文档信息抽取、交叉核验、结构化报告生成方面的能力，恰好匹配审批流程中"材料阅读 → 信息核对 → 意见书起草"这部分高耗时、机械性的工作。将 LLM 引入审批链路，让审批员从"读材料、写报告"升级为"审意见、做决策"，是当前行业提效的共识方向。

方案定位（核心决策）

  • AI 辅助 + 人工复核：LLM 不做最终放款决策。放款决策权保留在"规则引擎 + 评分卡 + 人工审批员"，LLM 负责材料智能审核与审批意见书生成。理由：
    1. 幻觉风险：LLM 可能编造数据，直接决策存在资损风险；
    2. 监管合规：信贷决策需满足可解释性、可问责性要求，人工干预是底线；
    3. 权责清晰：AI 提供意见与证据链，审批员对结论负责。

  3. 模型选型上，金融行业均选择私有化部署，数据不出域是共性底线。

2.2 非功能性需求

安全需求

  • 个人信息保护：遵循《个人信息保护法》，申请人数据全程加密存储与传输，训练/评测数据使用前必须脱敏（姓名、身份证号、手机号、银行卡号、地址等标识字段）
  • 数据不出域：LLM 私有化部署于公司机房，数据不出境、不出域；禁止调用任何外部公有云大模型 API
  • 访问控制：审批工作台按角色分级授权（审批员/复核主管/管理员），操作留痕可审计
  • 征信合规：人行征信数据仅用于本笔审批用途，用后按监管要求处理，不得留存用于模型训练

数据需求

  • 埋点数据：审批链路各节点耗时（AI 环节、人工环节分段统计）、审批员操作路径（查看证据链次数、驳回原因分布）
  • 正例数据：AI 意见被人工采纳的记录（采纳 = 代表人工认可 AI 结果），用于评测集扩充
  • 业务数据：审批时效、单笔成本、采纳率、通过率、坏账率、投诉率，用于验证 PM 价值

5.3 选型结论

  • 主模型：Qwen2.5-72B-Instruct。理由：
    1. 效果满足目标（评测集 92 分，接近 DeepSeek-V3，可通过 Prompt 与知识库优化补齐）；
    2. 部署成本最低：2 张 80G 显存 GPU 即可私有化部署，适合公司现有算力规模；
    3. 商用许可清晰，无商务谈判周期。
  • 备用模型（fallback）：Qwen2.5-14B-Instruct。与主模型同生态，Prompt 完全兼容，单卡可部署；主模型服务异常时自动切换，可用性优先、效果略降，对应 case 自动标记"AI 意见低置信"提示人工重点复核。
  • 成本核算（估算，GPU 摊销口径）：
    • 节点①材料审核：输入 3K / 输出 0.5K token ≈ 0.10 元/次
    • 节点②意见书生成：输入 5K / 输出 1K token ≈ 0.20 元/次
    • 合计约 0.30 元/单，满足 ≤ 0.5 元/单预算；对应日 2 万笔进件，AI 环节日成本约 6000 元，远低于节约的人工成本。

六、Prompt 工程设计

Prompt 是 AI 产品的核心交付物之一，必须文档化管理，不能留到"调试时"。Prompt 变更必须跑评测集验证，达标后方可发布，禁止未经评测的 Prompt 上线。

6.1 System Prompt 设计

  • 角色定义：资深信贷审批助理——在持牌消费金融机构有 10 年经验的审批专家，职责是协助审批员完成材料审核与意见书撰写。明确没有放款决策权，只提供分析意见供人工复核参考。
  • 输入约束：JSON 结构化字段，包含脱敏后的申请人信息、征信摘要、收入证明 OCR 结果、银行流水摘要、反欺诈筛查结果、产品规则（额度区间/利率档位/期限）。
  • 输出约束：严格 JSON schema（见下方示例），不输出任何非 JSON 文本；数字必须原样引用输入字段值。
  • 核心指令（按优先级）：
    1. 所有数字必须原样引用输入字段，禁止自行计算、推算、编造；
    2. 输入未提供的信息一律标注"未提供"，禁止推测；
    3. 只输出"建议"而非"结论"，最终结论由规则引擎与人工审批员做出；
    4. 禁止歧视性表述（年龄、性别、地域、民族、职业等）；
    5. 禁止任何承诺放款或承诺结果的表述。

System Prompt 示例

# 角色
你是一名在持牌消费金融机构工作 10 年的资深信贷审批助理，负责协助审批员完成个人消费贷进件的材料审核与审批意见书撰写。你没有放款决策权，只提供分析意见供人工复核参考。

# 输入
你会收到一段 JSON，字段如下：
{
  "apply_id": "申请单号",
  "applicant": {"age": 年龄, "region": "地区", "job_type": "职业类型", "apply_amount": 申请金额, "apply_term": 申请期限},
  "credit_report": {"overdue_count": 逾期次数, "overdue_days_max": 最大逾期天数, "total_loan_count": 贷款笔数, "credit_limit_usage": "授信使用率"},
  "income_proof": {"monthly_income": 月收入, "company": "单位名称", "employment_years": 工作年限},
  "bank_flow": {"monthly_avg_in": 月均流入, "monthly_avg_out": 月均流出, "salary_mark": "是否有工资字样流水"},
  "fraud_check": {"blacklist": "是否命中黑名单", "multi_loan_platforms": 多头借贷平台数},
  "product_rule": {"amount_range": [额度下限, 额度上限], "rate_tiers": ["利率档位1", "利率档位2"], "term_range": [期限下限, 期限上限]}
}

# 核心规则（最高优先级，违反任意一条即视为任务失败）
1. 你输出的所有数字必须原样引用输入 JSON 中的字段值，禁止自行计算、推算或编造任何数字。
2. 输入中没有的信息，一律标注"未提供"，禁止推测。
3. 你没有决策权：输出"建议"而非"结论"，最终结论由规则引擎与人工审批员做出。
4. 禁止出现歧视性表述（涉及年龄、性别、地域、民族、职业等）。
5. 禁止任何承诺放款或承诺结果的表述。

# 任务
1. 交叉核验材料一致性：身份信息、收入证明、银行流水之间是否互相矛盾。
2. 识别风险点：对每个风险点给出"证据字段 + 判断依据"。
3. 生成审批建议：建议结论、建议额度、建议利率档位，附置信度。

# 输出格式
严格输出以下 JSON，不要输出任何其他文字或解释：
{
  "apply_id": "string，原样引用输入",
  "consistency_check": {
    "result": "一致 | 存在矛盾",
    "issues": [
      {"field": "string，矛盾涉及字段", "evidence": "string，引用输入字段原文", "severity": "高 | 中 | 低"}
    ]
  },
  "risk_points": [
    {"point": "string，风险点描述", "evidence": "string，引用输入字段原文", "suggestion": "string，给人工复核的建议动作"}
  ],
  "recommendation": {
    "suggested_decision": "通过 | 拒绝 | 人工重点复核",
    "suggested_amount": "number，必须落在产品规则 amount_range 内且不高于申请金额",
    "suggested_rate_tier": "string，必须来自产品规则 rate_tiers 列表",
    "confidence": "0 到 1 的小数"
  },
  "uncertain_items": ["string，输入缺失或存疑、需人工确认的事项"]
}

6.2 Prompt 策略

策略是否采用说明
Few-shot 示例是静态精选 5 例（通过/拒绝/存疑场景各覆盖，含 1 例材料矛盾的边界案例），随 Prompt 版本统一管理
Chain-of-Thought部分采用不要求模型展示推理过程（内部思维链不外露，防止审批策略被逆向），仅要求输出"判断依据"字段，由依据驱动结论
结构化输出（JSON）是输出 schema 见 6.1，工程侧做 JSON Schema 校验
多步链式调用是两步链式：材料审核 → 意见书生成（调用逻辑见系统流程图）；审核未通过则不再调用意见书节点

6.3 Prompt 版本管理

版本更新内容负责人灰度
v1.0基线版本：材料审核 + 意见书生成彭勤双跑期（意见仅内部参考）
v1.1（规划）优化流水与收入矛盾场景 3 分彭勤灰度 10%

Prompt 变更流程：变更申请 → 离线评测集验证（达标标准见第八章）→ 小流量灰度 10% 观察一周 → 全量。禁止未经评测的 Prompt 上线。

八、评测体系

评测集是 AI 产品最核心的资产之一。本产品涉及资金风险，评测标准从严：数字幻觉零容忍、合规违规零容忍。

8.2 评测执行流程

  • 触发条件：
    • 模型版本升级 → 必须跑全量评测集
    • 线上 Bad Case 累计 ≥ 10 条 → 触发专项评测
    • 周期性回归：每月至少一次全量评测
    • Prompt 版本变更 → 必须跑全量评测集（强制）

8.3 评测维度与标准

评测维度评分标准合格线

可解释性每条结论是否可溯源到证据字段100%

8.4 评测集维护机制

  • Bad Case 回流：线上 Bad Case 每周回流到评测集，标注后纳入下一轮评测
  • 场景扩展同步：每次新增功能场景（如反欺诈线索分析）时，同步扩充对应的评测集
  • 版本管理：评测集使用版本号管理（如 eval_v1.0、eval_v1.1），与 Prompt 版本关联
  • 定期清理：每季度审查评测集，剔除过时用例（如已下架产品规则对应的用例），确保时效性

十、产品上线与迭代

产品能力说明

  • 一期（P0）上线"AI 辅助审批"主链路：材料智能审核 → 审批意见书生成 → 人工复核工作台，覆盖全量个人消费贷进件；
  • 二期（P1/P2）扩展反欺诈线索分析、拒件原因解释生成、客户问询与贷后预警。

灰度方案（阶段式）

阶段范围方案通过标准
阶段一双跑全量进件AI 意见仅内部生成，不呈现给审批员；对比 AI 意见与人工实际决策的一致性一致率 ≥ 90%，稳定运行 2 周
阶段二试点10% 进件审批工作台呈现 AI 意见，人工决定是否采纳；采纳行为埋点统计采纳率 ≥ 80%，无投诉增加，试点 2 周
阶段三 A/B 实验50% / 50%A 组（有 AI 辅助）vs B 组（无 AI 辅助），对比时效、成本、一致性、风险指标A 组时效/成本显著更优，风险不劣化，实验 4 周
阶段四全量100%全量上线，持续监控监控指标达标

迭代机制

  • Bad Case 周回流：审批员驳回的 AI 意见每周汇总分析 → 分类（Prompt 问题/知识库缺失/模型能力）→ 更新 Prompt 或知识库 → 评测集验证 → 灰度发布；
  • Prompt 版本管理：按 6.3 版本管理表执行，每次变更必须跑全量评测集；
  • 模型升级评估：每季度重新评估模型选型（对比新发布模型的效果与成本），触发全量评测。

上线监控指标

指标监控方式异常阈值
AI 意见采纳率工作台埋点< 80% 告警
AI 环节耗时/超时率链路埋点超时率 > 5% 告警
人工复核差错率质检抽检上线后较基线上升告警

通过率 / 坏账率业务数据出现显著劣化即回滚灰度

回滚机制：任何异常告警触发后，支持一键回滚至上一灰度版本（回退到纯人工审批流程），保障业务连续性优先。
